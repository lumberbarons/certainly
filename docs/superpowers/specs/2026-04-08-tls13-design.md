# Certainly TLS 1.3 Extension — Design Specification

**Date:** 2026-04-08
**Status:** Approved
**Depends on:** `2026-04-07-certainly-tls-library-design.md` (Phase 1, complete)

## Overview

Add TLS 1.3 (RFC 8446) client support to Certainly, the TLS library for classic Mac OS 9. The public API remains unchanged — `MacTLS_Create` / `MacTLS_Pump` / `MacTLS_Read` / `MacTLS_Write` / `MacTLS_Close` automatically negotiate the best TLS version the server supports (1.3 preferred, 1.2 fallback).

### Goals

- 1-RTT TLS 1.3 handshake with X25519 key exchange
- AES-128-GCM, AES-256-GCM, and ChaCha20-Poly1305 cipher suites
- Certificate verification with RSA-PSS and ECDSA signatures
- Automatic fallback to TLS 1.2 for servers that don't support 1.3
- No new public API — transparent to application code
- No malloc — all state lives in the existing `MacTLS_Context` allocation

### Non-Goals (v1)

- 0-RTT (early data) — complex replay attack surface, needs session storage
- PSK session resumption — needs persistent ticket storage, good v2 optimization
- HelloRetryRequest handling — abort on HRR (extremely rare with X25519)
- Post-handshake client authentication — we don't do client certificates
- Ed25519/Ed448 signatures — servers accept RSA-PSS and ECDSA
- Certificate compression — nice-to-have, not essential

## Architecture

### Version Negotiation

TLS 1.3 changed how version negotiation works. Instead of the version field in ClientHello (which stays at 0x0303 / "TLS 1.2" for middlebox compatibility), the client sends a `supported_versions` extension listing the versions it supports.

The negotiation flow:

1. `certainly.c` sends a ClientHello with:
   - Legacy version field: 0x0303 (TLS 1.2) — for middlebox compatibility
   - `supported_versions` extension: [0x0304 (TLS 1.3), 0x0303 (TLS 1.2)]
   - `key_share` extension: X25519 public key (optimistic, assuming server picks 1.3)
   - All existing TLS 1.2 extensions (SNI, signature algorithms, etc.)

2. The server's response determines the path:
   - If ServerHello contains `supported_versions` with 0x0304 → TLS 1.3 path
   - If ServerHello has version 0x0303 and no `supported_versions` → TLS 1.2 path (existing BearSSL code)

3. On the TLS 1.3 path, control transfers to `tls13_handshake.c`. On TLS 1.2, the existing BearSSL handshake continues unchanged.

### Component Overview

```
MacTLS_Pump()
    |
    ├── OT Transport (unchanged)
    |
    ├── BearSSL engine (record I/O unchanged)
    |
    └── Handshake routing:
            |
            ├── ServerHello has supported_versions 0x0304?
            |       |
            |       YES → tls13_handshake.c (NEW)
            |       |       ├── tls13_keysched.c (key derivation)
            |       |       ├── tls13_record.c (1.3 record format)
            |       |       └── x509_minimal patch (RSA-PSS)
            |       |
            |       NO → BearSSL ssl_hs_client (existing TLS 1.2, unchanged)
            |
            └── After handshake: same MacTLS_Read/Write/Close
```

## Handshake State Machine

### Message Flow (1-RTT)

```
Client                                              Server
  |                                                    |
  | ---- ClientHello + key_share + supported_versions ->
  |                                                    |
  | <- ServerHello + key_share + supported_versions ---
  |    [derive handshake keys, switch to encrypted]    |
  | <- EncryptedExtensions (encrypted) ----------------
  | <- Certificate (encrypted) ------------------------
  | <- CertificateVerify (encrypted) ------------------
  | <- Finished (encrypted) ---------------------------
  |                                                    |
  |    [verify server, derive application keys]        |
  | ---- Finished (encrypted) -----------------------> |
  |    [switch to application keys]                    |
  |                                                    |
  | ============= ENCRYPTED TUNNEL =================== |
```

### State Table

The handshake is implemented as a table-driven state machine (following LibreSSL's design pattern). Each state specifies a send or receive function:

```c
enum tls13_state {
    kTLS13_SendClientHello,
    kTLS13_RecvServerHello,
    kTLS13_RecvEncryptedExtensions,
    kTLS13_RecvCertificate,
    kTLS13_RecvCertificateVerify,
    kTLS13_RecvFinished,
    kTLS13_SendFinished,
    kTLS13_Complete
};
```

Each state handler:
- Reads or writes a handshake message
- Updates the transcript hash
- May trigger a key derivation step
- Returns: `OK` (advance to next state), `WANT_READ` (need more data from network), `WANT_WRITE` (have data to send), or `ERROR`

The pump loop in `certainly.c` calls the current state handler, feeds BearSSL's record layer as before, and advances through the table.

### Key Derivation Points

The handshake triggers key derivation at specific moments:

| After receiving | We derive | Used for |
|---|---|---|
| ServerHello | Handshake traffic keys | Decrypting EncryptedExtensions, Certificate, CertificateVerify, Finished from server |
| Server Finished | Application traffic keys | Encrypting/decrypting actual HTTP data |

Each derivation uses HKDF (BearSSL's existing implementation) with the transcript hash as input, binding the keys to the exact conversation.

## Key Schedule

### What HKDF Does

HKDF (HMAC-based Key Derivation Function) takes raw cryptographic material and produces clean, uniform keys. It works in two steps:

- **Extract**: Compress variable-length input into a fixed-length pseudorandom key using HMAC
- **Expand**: Stretch that key into multiple output keys, each labeled for its purpose

### TLS 1.3 Key Schedule Flow

```
PSK (or zeros if no PSK)
         |
   HKDF-Extract
         |
         v
    Early Secret -----> [not used in our implementation]
         |
   HKDF-Extract  <---- DH shared secret (from X25519)
         |
         v
   Handshake Secret
    /           \
Derive-Secret  Derive-Secret   (using transcript hash up to ServerHello)
"c hs traffic" "s hs traffic"
    |               |
    v               v
Client HS Key   Server HS Key   (+ IVs for each)
    |
   HKDF-Extract  <---- (zeros)
    |
    v
   Master Secret
    /           \
Derive-Secret  Derive-Secret   (using transcript hash up to Server Finished)
"c ap traffic" "s ap traffic"
    |               |
    v               v
Client App Key  Server App Key  (+ IVs for each)
```

### Derive-Secret

`Derive-Secret(secret, label, transcript_hash)` is a wrapper around HKDF-Expand-Label that produces a key from:
- The current secret (output of the previous Extract step)
- A text label (like "c hs traffic" meaning "client handshake traffic")
- The transcript hash (SHA-256 of all handshake messages so far)

This binding to the transcript hash is what makes TLS 1.3's key derivation tamper-proof — any modification to any handshake message changes the hash, which changes all derived keys, which breaks the connection.

### Key Schedule API

```c
typedef struct {
    const br_hash_class *hash;      /* SHA-256 or SHA-384 */
    size_t              hash_len;   /* 32 or 48 */
    unsigned char       secret[64]; /* current secret (max hash output) */
    unsigned char       transcript_hash[64];
} tls13_keysched;

void tls13_ks_init(tls13_keysched *ks, const br_hash_class *hash);
void tls13_ks_extract_early(tls13_keysched *ks);
void tls13_ks_extract_handshake(tls13_keysched *ks,
                                const void *shared_secret, size_t len);
void tls13_ks_derive_handshake_keys(tls13_keysched *ks,
                                    const void *transcript_hash,
                                    void *client_key, void *client_iv,
                                    void *server_key, void *server_iv);
void tls13_ks_extract_master(tls13_keysched *ks);
void tls13_ks_derive_app_keys(tls13_keysched *ks,
                              const void *transcript_hash,
                              void *client_key, void *client_iv,
                              void *server_key, void *server_iv);
void tls13_ks_derive_finished_key(tls13_keysched *ks,
                                  const void *base_key,
                                  void *finished_key);
```

No malloc — `tls13_keysched` is a fixed-size struct embedded in the handshake context.

## Record Layer (TLS 1.3 Format)

### Differences from TLS 1.2

| Aspect | TLS 1.2 | TLS 1.3 |
|---|---|---|
| Outer content type | Real type (handshake, app data, alert) | Always 0x17 (application_data) — disguised |
| Outer version | 0x0303 | 0x0303 (same, for middlebox compat) |
| Real content type | In the header | Hidden inside encrypted payload (last byte) |
| Nonce | Explicit 8 bytes per record | Implicit: IV XOR sequence number |
| AAD (authenticated data) | seq_num + type + version + length | Just: type + version + length |

### Implementation

Two new record handler implementations that plug into BearSSL's existing vtable interface:

```c
/* Decrypt incoming TLS 1.3 records */
typedef struct {
    const br_sslrec_in_class *vtable;
    /* cipher context (GCM or ChaPol) */
    /* IV, sequence counter */
} tls13_rec_in_context;

/* Encrypt outgoing TLS 1.3 records */
typedef struct {
    const br_sslrec_out_class *vtable;
    /* cipher context (GCM or ChaPol) */
    /* IV, sequence counter */
} tls13_rec_out_context;
```

The actual encryption/decryption calls the same BearSSL AES-GCM or ChaCha20-Poly1305 functions used by TLS 1.2. Only the envelope format and nonce computation differ.

## RSA-PSS Support

### What Needs Wiring

BearSSL's RSA-PSS verification code exists (`br_rsa_pss_vrfy`) but is not connected to:

1. **The X.509 certificate validator** (`x509_minimal`) — needs to recognize RSA-PSS OIDs when verifying certificate chain signatures. Currently only PKCS#1 v1.5 OIDs are recognized.

2. **The TLS 1.3 CertificateVerify handler** — needs to call `br_rsa_pss_vrfy` to verify the server's proof of identity.

### Changes

- Patch `bearssl/src/x509/x509_minimal.t0` (the T0 source) to add RSA-PSS OID recognition and call `br_rsa_pss_vrfy` via a new function pointer in the engine context. Recompile with the T0 compiler to regenerate `x509_minimal.c`.
- **Chosen approach:** Patch the generated `x509_minimal.c` directly. The T0 compiler is a custom Java tool with no documentation, and setting it up for one patch is not worth the complexity. We'll add a comment in the patched file noting what was changed and why.
- Add RSA-PSS verification call in `tls13_handshake.c` state 5 (CertificateVerify).

## Transcript Hashing

### What It Is

A running SHA-256 (or SHA-384) hash over every handshake message sent and received, in order. At specific points during the handshake, the current hash value is "snapshotted" and used as input to key derivation.

### Implementation

```c
typedef struct {
    br_sha256_context sha256;   /* running hash context */
} tls13_transcript;

void tls13_transcript_init(tls13_transcript *t);
void tls13_transcript_update(tls13_transcript *t,
                             const void *msg, size_t len);
void tls13_transcript_snapshot(const tls13_transcript *t,
                               void *out_hash);
```

The transcript context lives inside the handshake state. Each time a handshake message is sent or received, it's fed into the hash. When key derivation needs the transcript hash, we take a snapshot (copy the hash state, finalize the copy, keep the original running).

## Memory Layout

The TLS 1.3 handshake state lives inside `MacTLS_Context`:

```c
struct MacTLS_Context {
    /* ... existing fields ... */

    /* TLS 1.3 handshake state (only used during handshake) */
    struct {
        enum tls13_state    state;
        tls13_keysched      ks;
        tls13_transcript    transcript;

        /* Our ephemeral X25519 key pair */
        unsigned char       ecdhe_secret[32];  /* private key */
        unsigned char       ecdhe_public[32];  /* sent in ClientHello */

        /* Handshake traffic keys (used during handshake) */
        unsigned char       client_hs_key[32];
        unsigned char       client_hs_iv[12];
        unsigned char       server_hs_key[32];
        unsigned char       server_hs_iv[12];

        /* Buffer for assembling/parsing handshake messages */
        unsigned char       msg_buf[4096];
        size_t              msg_len;
        size_t              msg_offset;

        /* Negotiated cipher suite */
        uint16_t            cipher_suite;
        bool                is_tls13;
    } hs13;
};
```

This adds roughly 4.3KB to `MacTLS_Context`. The total context size goes from ~17KB to ~21KB. No additional allocations.

## Cipher Suites

TLS 1.3 defines its own cipher suite identifiers (separate from TLS 1.2):

| Suite | ID | Our support |
|---|---|---|
| TLS_AES_128_GCM_SHA256 | 0x1301 | Yes |
| TLS_AES_256_GCM_SHA384 | 0x1302 | Yes |
| TLS_CHACHA20_POLY1305_SHA256 | 0x1303 | Yes |
| TLS_AES_128_CCM_SHA256 | 0x1304 | Skip (rarely used) |
| TLS_AES_128_CCM_8_SHA256 | 0x1305 | Skip (IoT only) |

Note: TLS 1.3 cipher suites don't include the key exchange or signature algorithm — those are negotiated separately via extensions. This is simpler than TLS 1.2 where the cipher suite bundled everything together.

## Testing Strategy

1. **Host-side unit tests** for key schedule: implement HKDF test vectors from RFC 8446 Appendix A, verify our key derivation matches known-good outputs.

2. **PPC integration test**: connect to a TLS 1.3-only test server (e.g., `tls13.1d.pw` or `enabled.tls13.com`) from Mac OS 9 in SheepShaver.

3. **Fallback test**: connect to a TLS 1.2-only server and verify fallback works (existing SimpleGet test).

4. **Wireshark verification**: capture the handshake on the host side and verify correct TLS 1.3 message sequence.
