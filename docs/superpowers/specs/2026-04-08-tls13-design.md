# Certainly TLS 1.3 Extension — Design Specification

**Date:** 2026-04-08
**Status:** Approved (rev2 — post security review)
**Depends on:** `2026-04-07-certainly-tls-library-design.md` (Phase 1, complete)

## Overview

Add TLS 1.3 (RFC 8446) client support to Certainly, the TLS library for classic Mac OS 9. The public API remains unchanged — `MacTLS_Create` / `MacTLS_Pump` / `MacTLS_Read` / `MacTLS_Write` / `MacTLS_Close` automatically negotiate the best TLS version the server supports (1.3 preferred, 1.2 fallback).

### Goals

- 1-RTT TLS 1.3 handshake with X25519 key exchange
- AES-128-GCM, AES-256-GCM, and ChaCha20-Poly1305 cipher suites
- Certificate verification with RSA-PSS and ECDSA signatures
- Automatic fallback to TLS 1.2 for servers that don't support 1.3
- Middlebox compatibility mode (CCS messages)
- HelloRetryRequest with cookie support
- No new public API — transparent to application code
- No malloc — all state lives in the existing `MacTLS_Context` allocation

### Non-Goals (v1)

- 0-RTT (early data) — complex replay attack surface, needs session storage. If server sends `early_data` extension in EncryptedExtensions, silently ignore it.
- PSK session resumption — needs persistent ticket storage, good v2 optimization. NewSessionTicket messages from server are silently discarded.
- Post-handshake client authentication — we don't do client certificates. CertificateRequest from server is accepted and skipped (empty Certificate response).
- Ed25519/Ed448 signatures — servers accept RSA-PSS and ECDSA
- Certificate compression — nice-to-have, not essential
- KeyUpdate — for short-lived HTTPS connections, key rotation is unnecessary. If server sends KeyUpdate, treat as connection close.

## Architecture

### ClientHello Construction — Bypassing BearSSL's T0 Handshake

BearSSL's ClientHello is built by T0 bytecode deep inside `ssl_hs_client.c`. There is no extension callback mechanism to inject TLS 1.3 extensions. Rather than patching the T0 bytecode, **the TLS 1.3 path constructs its own ClientHello from scratch** and uses BearSSL only for:

- Record-level I/O (sendrec/recvrec buffers)
- Crypto primitives (HKDF, ECDHE, AES-GCM, ChaCha20, SHA-256, RSA-PSS verify)
- X.509 certificate validation (with RSA-PSS patch)

The TLS 1.3 handshake code manages the engine's state directly, setting the `application_data` flag and record encryption vtables at the appropriate points.

**For TLS 1.2 fallback:** If the server responds with a TLS 1.2 ServerHello (no `supported_versions` extension), we must restart the handshake using BearSSL's T0 engine. This means the initial ClientHello sent by our TLS 1.3 code must be compatible with TLS 1.2 (include all 1.2 cipher suites and extensions alongside the 1.3 ones). On fallback, we re-initialize BearSSL's client context and replay the ServerHello through the T0 engine.

### Version Negotiation

1. Our code builds a ClientHello with:
   - Legacy version field: 0x0303 (TLS 1.2) — for middlebox compatibility
   - `supported_versions` extension: [0x0304 (TLS 1.3), 0x0303 (TLS 1.2)]
   - `supported_groups` extension: [X25519 (0x001D)]
   - `key_share` extension: X25519 public key (optimistic, for 1.3)
   - `signature_algorithms` extension with TLS 1.3 scheme values:
     - `rsa_pss_rsae_sha256` (0x0804)
     - `rsa_pss_rsae_sha384` (0x0805)
     - `ecdsa_secp256r1_sha256` (0x0403)
     - `ecdsa_secp384r1_sha384` (0x0503)
     - `rsa_pkcs1_sha256` (0x0401) — for cert chain verification only
     - `rsa_pkcs1_sha384` (0x0501) — for cert chain verification only
   - SNI, TLS 1.2 cipher suites (for fallback compatibility)

2. Send CCS immediately after ClientHello (middlebox compatibility mode).

3. Parse ServerHello:
   - If `supported_versions` contains 0x0304 → TLS 1.3 path
   - If ServerHello version is 0x0303, no `supported_versions` → TLS 1.2 fallback
   - Accept and ignore CCS from server at any point

### Component Overview

```
MacTLS_Pump()
    |
    ├── OT Transport (unchanged)
    |
    ├── Record I/O: use BearSSL's recvrec/sendrec buffers directly
    |   (NOT through BearSSL's T0 handshake processor)
    |
    └── Handshake routing:
            |
            ├── ServerHello has supported_versions 0x0304?
            |       |
            |       YES → tls13_handshake.c (NEW)
            |       |       ├── tls13_keysched.c (key derivation)
            |       |       ├── tls13_record.c (1.3 record format)
            |       |       └── x509_minimal patch (RSA-PSS)
            |       |

            |

```

## Handshake State Machine

### Message Flow (1-RTT)

```
Client                                              Server
  |                                                    |
  | ---- ClientHello ------------------------------>   |
  | ---- CCS (middlebox compat, ignored by server) ->  |
  |                                                    |
  | <--- ServerHello --------------------------------  |
  | <--- CCS (middlebox compat, we ignore it) ------  |
  |    [derive handshake keys, switch to encrypted]    |
  | <--- EncryptedExtensions (encrypted) -----------  |
  | <--- CertificateRequest (encrypted, optional) --  |
  | <--- Certificate (encrypted) -------------------  |
  | <--- CertificateVerify (encrypted) -------------  |
  | <--- Finished (encrypted) ----------------------  |
  |                                                    |
  |    [verify server, derive application keys]        |
  | ---- Finished (encrypted) --------------------->   |
  |    [switch to application keys]                    |
  |                                                    |
  | ============= ENCRYPTED TUNNEL =================== |
  |                                                    |
  | <--- NewSessionTicket (encrypted, we discard) --  |
```

### State Table

```c
enum tls13_state {
    kTLS13_SendClientHello,
    kTLS13_SendCCS,               /* middlebox compatibility */
    kTLS13_RecvServerHello,
    kTLS13_RecvEncryptedExtensions,
    kTLS13_RecvCertRequestOrCert, /* CertificateRequest is optional — skip or recv Certificate */
    kTLS13_RecvCertificate,
    kTLS13_RecvCertificateVerify,
    kTLS13_RecvFinished,
    kTLS13_SendFinished,
    kTLS13_Complete
};
```

The `kTLS13_RecvCertRequestOrCert` state peeks at the handshake message type byte:
- If `certificate_request` (type 13): parse and discard, advance to `kTLS13_RecvCertificate`
- If `certificate` (type 11): skip to `kTLS13_RecvCertificate` directly

### HelloRetryRequest Handling

If the server sends HelloRetryRequest instead of ServerHello:
- If it contains a `cookie` extension: re-send ClientHello with the cookie included. Reset transcript hash with a special synthetic `message_hash` construct per RFC 8446 Section 4.4.1.
- If it requests a different key share group: abort (we only support X25519 and P-256-only servers are extremely rare).

This handles the Cloudflare DoS protection case (cookie-based HRR) which is the primary real-world HRR scenario.

### Post-Handshake Message Handling

After the handshake completes and the connection enters `kMacTLS_Connected` state, the server may send:
- **NewSessionTicket**: silently discard (PSK resumption is a non-goal)
- **KeyUpdate**: treat as connection close (short-lived HTTPS connections don't need key rotation)

These arrive as handshake-type records (inner content type 0x16) during the application data phase. The TLS 1.3 record layer must unwrap them and dispatch appropriately rather than treating non-application-data as an error.

### Key Derivation Points

| After receiving | We derive | Used for |
|---|---|---|
| ServerHello | Handshake traffic keys | Decrypting EncryptedExtensions, Certificate, CertificateVerify, Finished from server. Encrypting our Finished message. |
| Server Finished | Application traffic keys | Encrypting/decrypting actual HTTP data |

## Key Schedule

### TLS 1.3 Key Schedule Flow (corrected per RFC 8446 Section 7.1)

Note the `Derive-Secret(., "derived", "")` steps between each Extract. These use the hash of an empty string (NOT the transcript) and are required for domain separation. Without them, derived keys will not match any server.

```
0 (zeros, no PSK)
         |
   HKDF-Extract
         |
         v
    Early Secret
         |
   Derive-Secret(., "derived", "")   ← hash of empty string, NOT transcript
         |
   HKDF-Extract  <---- DH shared secret (from X25519)
         |
         v
   Handshake Secret
    /           \
Derive-Secret  Derive-Secret   (using transcript hash up to ServerHello)
"c hs traffic" "s hs traffic"
    |               |
    v               v
Client HS Key   Server HS Key   (+ IVs for each)
         |
   Derive-Secret(., "derived", "")   ← hash of empty string again
         |
   HKDF-Extract  <---- 0 (zeros)
         |
         v
   Master Secret
    /           \
Derive-Secret  Derive-Secret   (using transcript hash up to Server Finished)
"c ap traffic" "s ap traffic"
    |               |
    v               v
Client App Key  Server App Key  (+ IVs for each)
```

### Key Schedule API

```c
typedef struct {
    const br_hash_class *hash;      /* SHA-256 or SHA-384 */
    size_t              hash_len;   /* 32 or 48 */
    unsigned char       secret[64]; /* current secret (max hash output) */
    unsigned char       empty_hash[64]; /* precomputed Hash("") */
} tls13_keysched;

/* Init precomputes Hash("") for the chosen hash function */
void tls13_ks_init(tls13_keysched *ks, const br_hash_class *hash);

/* Early Secret: HKDF-Extract(0, 0) */
void tls13_ks_extract_early(tls13_keysched *ks);

/* Handshake Secret: Derive-Secret(early, "derived", "") then
   HKDF-Extract(derived, shared_secret) */
void tls13_ks_extract_handshake(tls13_keysched *ks,
                                const void *shared_secret, size_t len);

/* Derive client/server handshake traffic keys from transcript hash */
void tls13_ks_derive_handshake_keys(tls13_keysched *ks,
                                    const void *transcript_hash,
                                    void *client_key, void *client_iv,
                                    void *server_key, void *server_iv);

/* Master Secret: Derive-Secret(handshake, "derived", "") then
   HKDF-Extract(derived, 0) */
void tls13_ks_extract_master(tls13_keysched *ks);

/* Derive client/server application traffic keys from transcript hash */
void tls13_ks_derive_app_keys(tls13_keysched *ks,
                              const void *transcript_hash,
                              void *client_key, void *client_iv,
                              void *server_key, void *server_iv);

/* Derive the Finished verification key from a traffic secret */
void tls13_ks_derive_finished_key(tls13_keysched *ks,
                                  const void *base_key,
                                  void *finished_key);
```

The `extract_handshake` and `extract_master` functions internally call `Derive-Secret(current, "derived", empty_hash)` before the Extract step. This is encapsulated — callers don't need to know about the intermediate derivation.

## Record Layer (TLS 1.3 Format)

### Differences from TLS 1.2

| Aspect | TLS 1.2 | TLS 1.3 |
|---|---|---|
| Outer content type | Real type (handshake, app data, alert) | Always 0x17 (application_data) — disguised |
| Outer version | 0x0303 | 0x0303 (same, for middlebox compat) |
| Real content type | In the header | Hidden inside encrypted payload (last byte) |
| Nonce | Explicit 8 bytes per record | Implicit: IV XOR sequence number |
| AAD | seq_num + type + version + length | type (0x17) + version (0x0303) + ciphertext length (includes content type byte + 16-byte AEAD tag) |

Note: the `length` in TLS 1.3 AAD is the ciphertext length, not the plaintext length. This is a critical implementation detail.

### Integration with BearSSL's Record Layer

BearSSL's record dispatch uses `br_sslrec_in_class` / `br_sslrec_out_class` vtables stored in unions inside `br_ssl_engine_context`. The TLS 1.3 path **does NOT use BearSSL's record dispatch**. Instead:

1. We read raw encrypted records from BearSSL's `recvrec` buffer
2. Decrypt them ourselves using BearSSL's AES-GCM / ChaCha20-Poly1305 primitives directly
3. Feed decrypted handshake/application data into our own processing
4. For sending: encrypt data ourselves and write to BearSSL's `sendrec` buffer

This avoids the vtable sizing constraint (BearSSL's record context unions may not fit our types) and gives us full control over the mid-handshake encryption switches. After the handshake completes and we enter the application data phase, we install our TLS 1.3 record handlers so that `MacTLS_Read` / `MacTLS_Write` work through the normal pump loop.

### Encryption Switches During Handshake

The handshake requires switching encryption at three points:

| Point | Read direction | Write direction |
|---|---|---|
| After ServerHello | Switch to server handshake keys | Still plaintext |
| Before client Finished | Server handshake keys | Switch to client handshake keys |
| After handshake complete | Switch to server app keys | Switch to client app keys |

Each switch installs new keys/IVs and resets the sequence counter to 0.

### Certificate Processing

Certificates are NOT buffered in `msg_buf`. They are streamed directly through BearSSL's X.509 minimal validator from the record buffer (`iobuf`, which is 16KB+). The `msg_buf` (4KB) is only used for non-certificate handshake messages (ServerHello, EncryptedExtensions, CertificateVerify, Finished — all under 1KB individually).

The streaming approach:
1. Record layer decrypts a record containing Certificate message fragments
2. Handshake code feeds certificate bytes directly into `br_x509_minimal_push()` as they arrive
3. After all certificates are pushed, call `br_x509_minimal_get_pkey()` to get the validated public key
4. No need to buffer the entire certificate chain in memory

## RSA-PSS Support

### Changes

- **Patch `bearssl/src/x509/x509_minimal.c` directly** (not the T0 source). Add RSA-PSS OID recognition in the signature algorithm switch. The T0 compiler is a custom Java tool with no documentation; setting it up for one patch is not worth the complexity. A comment in the patched file documents what was changed and why.
- Add RSA-PSS verification call in `tls13_handshake.c` CertificateVerify handler.
- The `signature_algorithms` extension in ClientHello lists RSA-PSS scheme IDs (0x0804, 0x0805) so servers know we support PSS signatures.

## Transcript Hashing

### Implementation

```c
typedef struct {
    br_sha256_context sha256;   /* running hash context (or sha384) */
    const br_hash_class *hash;  /* hash class for snapshots */
} tls13_transcript;

void tls13_transcript_init(tls13_transcript *t, const br_hash_class *hash);
void tls13_transcript_update(tls13_transcript *t,
                             const void *msg, size_t len);
void tls13_transcript_snapshot(const tls13_transcript *t,
                               void *out_hash);
```

For HelloRetryRequest, the transcript must be reset with a synthetic `message_hash` construct: `Hash(message_hash || 0x00 || uint24(hash_len) || Hash(ClientHello1))` per RFC 8446 Section 4.4.1.

## Memory Layout

```c
struct MacTLS_Context {
    /* ... existing fields ... */

    /* TLS 1.3 handshake state */
    struct {
        enum tls13_state    state;
        tls13_keysched      ks;
        tls13_transcript    transcript;

        /* Ephemeral X25519 key pair */
        unsigned char       ecdhe_secret[32];
        unsigned char       ecdhe_public[32];

        /* Traffic keys (handshake phase, then application phase) */
        unsigned char       client_key[32];
        unsigned char       client_iv[12];
        unsigned char       server_key[32];
        unsigned char       server_iv[12];

        /* Record sequence counters */
        uint64_t            read_seq;
        uint64_t            write_seq;

        /* Buffer for non-certificate handshake messages */
        unsigned char       msg_buf[4096];
        size_t              msg_len;
        size_t              msg_offset;

        /* HRR cookie (if server sends one) */
        unsigned char       cookie[256];
        size_t              cookie_len;

        /* Negotiated cipher suite and state */
        uint16_t            cipher_suite;
        bool                is_tls13;
        bool                hrr_received;
    } hs13;
};
```

Total addition: ~4.6KB. Context goes from ~17KB to ~22KB. No additional allocations.

## Cipher Suites

TLS 1.3 cipher suites (offered in ClientHello):

| Suite | ID | Our support |
|---|---|---|
| TLS_CHACHA20_POLY1305_SHA256 | 0x1303 | Yes (preferred — fastest on PPC) |
| TLS_AES_128_GCM_SHA256 | 0x1301 | Yes |
| TLS_AES_256_GCM_SHA384 | 0x1302 | Yes |
| TLS_AES_128_CCM_SHA256 | 0x1304 | Skip |
| TLS_AES_128_CCM_8_SHA256 | 0x1305 | Skip |

These are listed alongside TLS 1.2 cipher suites in the ClientHello for fallback compatibility.

## Testing Strategy

1. **Host-side unit tests** for key schedule: RFC 8446 Appendix A test vectors.
2. **PPC integration test**: connect to a TLS 1.3 server from Mac OS 9 in SheepShaver.
3. **Fallback test**: connect to TLS 1.2-only server, verify existing behavior preserved.
4. **HRR test**: connect through a server that sends HelloRetryRequest with cookie.
5. **Wireshark verification**: capture handshake, verify correct 1.3 message sequence including CCS.
6. **NewSessionTicket test**: verify post-handshake tickets are silently discarded.
